# 搜索系统实现方案

## 一、背景与目标

### 1.1 建设背景
随着知文内容规模的增长，传统的基于数据库的查询方式面临以下挑战:
- **对中文支持不友好**: 数据库 LIKE 查询无法有效处理中文分词
- **相关性排序困难**: 难以体现搜索结果与关键词的相关性强弱
- **业务扩展性差**: 难以支持高亮显示、联想建议等多种业务需求

### 1.2 建设目标
构建独立的搜索模块，实现:
- **搜得快**: 基于倒排索引的快速检索能力
- **搜得准**: 支持中文分词和相关性排序
- **可扩展**: 能够随业务发展灵活扩展搜索策略

## 二、技术选型

### 2.1 Elasticsearch
选择 Elasticsearch 作为搜索引擎，原因如下:
- **读写分离架构**: 写入异步不影响读取性能
- **强大的全文检索**: 原生支持中文分词 (IK Analyzer)
- **多字段检索**: 支持对不同字段设置不同权重
- **丰富的查询 DSL**: 支持复杂查询和聚合分析
- **水平扩展能力**: 可随数据量增长动态扩容

### 2.2 设计思想
采用**读优化策略**:
- 在写入 ES 索引时，将列表展示所需字段冗余到 ES 文档中
- 减少查询时的 DB 回表操作，提升读取性能
- 虽增加存储开销，但换取查询效率的大幅提升

### 3.2 核心组件

#### 3.2.1 接口层 (SearchController)
**位置**: `src/main/java/com/tongji/search/api/SearchController.java`

**职责**:
- 接收并解析 HTTP 请求参数
- 调用服务层进行搜索
- 返回标准化响应

**接口列表**:
```java
// 1. 关键词检索
GET /api/v1/search?q=关键词&size=20&tags=标签 1，标签 2&after=游标

// 2. 联想建议
GET /api/v1/search/suggest?prefix=前缀&size=10
```

**参数说明**:
- `q`: 搜索关键词 (必填)
- `size`: 返回条数 (默认 20，最小 1)
- `tags`: 标签过滤，逗号分隔 (可选)
- `after`: 游标分页，Base64URL 编码 (可选)
- `prefix`: 联想前缀 (必填)

#### 3.2.2 服务层 (SearchServiceImpl)
**位置**: `src/main/java/com/tongji/search/service/impl/SearchServiceImpl.java`

**核心功能**:

**1. 关键词检索 (`search`)**
- 构造 ES 查询 DSL
- 实现宽召回、业务过滤、业务加权策略
- 处理游标分页
- 构建高亮片段
- 封装响应数据

**查询策略**:
```java
// 复合排序：优先级从高到低
1. 相关性分数 (score) - 降序
2. 发布时间 (publish_time) - 降序
3. 点赞数 (like_count) - 降序
4. 浏览数 (view_count) - 降序
5. 内容 ID (content_id) - 降序 (保证稳定性)

// 布尔查询结构
must: multi_match(title^3, body)  // 标题权重是正文的 3 倍
filter: status = "published"       // 只查已发布
filter: tags IN [...]              // 标签过滤 (可选)

// 互动数据加权
function_score:
  - like_count * log1p(like_count) * 2.0
  - view_count * log1p(view_count) * 1.0
  boost_mode: sum
```

**2. 联想建议 (`suggest`)**
- 使用 ES Completion Suggester
- 基于 `title_suggest` 字段提供前缀匹配
- 返回候选标题列表

#### 3.2.3 索引管理服务 (SearchIndexService)
**位置**: `src/main/java/com/tongji/search/index/SearchIndexService.java`

**核心职责**:

**1. 索引初始化**
- 启动时检查索引是否存在
- 若不存在则创建索引并定义 Mapping

**2. 历史数据回灌**
```java
@PostConstruct
public void ensureBackfill() {
    // 分页读取已发布的知文数据
    // 批量写入 ES 索引
    // 直到所有历史数据同步完成
}
```

**3. 单条索引更新 (upsert)**
```java
public void upsertKnowPost(long id) {
    // 1. 从 DB 查询知文详情
    // 2. 组装 ES 文档 (含冗余字段)
    // 3. 获取计数数据 (点赞、收藏)
    // 4. 安全抓取正文内容 (容错处理)
    // 5. 写入 ES (wait_for 刷新策略)
}
```

**文档结构**:
```json
{
  "content_id": 123,                    // 知文 ID
  "content_type": "image_text",         // 内容类型
  "title": "标题",                       // 标题 (ik_max_word 分词)
  "description": "描述",                 // 描述
  "body": "正文内容",                    // 正文 (ik_max_word 分词)
  "author_id": 456,                     // 作者 ID
  "author_avatar": "头像 URL",           // 作者头像
  "author_nickname": "昵称",             // 作者昵称
  "author_tag_json": "[...]",           // 作者领域标签
  "publish_time": 1234567890000,        // 发布时间戳
  "status": "published",                // 状态
  "tags": ["标签 1", "标签 2"],           // 标签数组
  "img_urls": ["图片 1", "图片 2"],       // 图片 URL 数组
  "is_top": true,                       // 是否置顶
  "like_count": 100,                    // 点赞数
  "favorite_count": 50,                 // 收藏数
  "view_count": 1000,                   // 浏览数
  "title_suggest": "标题"               // 补全建议字段
}
```

**4. 软删除处理**
```java
public void softDeleteKnowPost(long id) {
    // 仅更新 status="deleted"
    // 同一文档 ID 覆盖写入，保持幂等性
}
```

#### 3.2.4 增量同步消费者 (CanalOutboxConsumerSearch)
**位置**: `src/main/java/com/tongji/search/outbox/CanalOutboxConsumerSearch.java`

**工作原理**:
```
MySQL (outbox 表) 
  → Canal 监听变更 
  → Kafka (canal-outbox 主题)
  → 消费者监听并更新 ES 索引
```

**消费逻辑**:
```java
@KafkaListener(topics = "canal-outbox", groupId = "search-index-consumer")
public void onMessage(String message, Acknowledgment ack) {
    // 1. 解析 Outbox 消息
    // 2. 提取 entity="knowpost" 的行
    // 3. 根据 op 类型执行:
    //    - op="delete": 软删除索引
    //    - op=其他：upsert 索引
    // 4. 提交 Kafka 位点
}
```

**关键特性**:
- **幂等性**: 同一文档 ID 覆盖写入
- **容错性**: 异常捕获不中断消费
- **实时性**: 监听数据变更即时更新索引

## 四、数据流

### 4.1 写入路径
```
1. 索引初始化
   └─> 应用启动 → 检查索引存在性 → 创建索引 (若不存在)

2. 历史数据回灌
   └─> 检查索引文档数 → 分页查询 DB → 批量 upsert → 完成

3. 增量更新
   └─> 知文发布/更新/删除
      → 写入 DB + Outbox 表
      → Canal 捕获变更
      → 发送到 Kafka
      → 消费者监听并更新 ES
```

### 4.2 查询路径
```
1. Controller 接收请求
   └─> 解析参数 (q, size, tags, after)
   └─> 提取当前用户 ID(用于个性化)

2. Service 构造查询
   └─> 解析标签过滤条件
   └─> 解码游标
   └─> 构建 bool + function_score 查询
   └─> 设置高亮字段

3. ES 返回结果
   └─> 执行查询
   └─> 返回命中结果 + 高亮片段 + sort 值

4. 转换封装
   └─> 提取 source 字段
   └─> 合并高亮片段为 snippet
   └─> 查询计数服务获取点赞/收藏状态
   └─> 封装 FeedItemResponse
   └─> 编码游标 (nextAfter)

5. 返回前端
   └─> SearchResponse(items, nextAfter, hasMore)
```

## 五、索引设计

### 5.1 Mapping 设计原则
遵循**检索用 Text + 分词，过滤/排序/展示用 Keyword**的原则:

| 字段 | 类型 | 分词器 | 用途说明 |
|------|------|--------|----------|
| `content_id` | long | - | 内容唯一标识，用于去重和稳定排序 |
| `content_type` | keyword | - | 内容类型，用于过滤 |
| `title` | text | ik_max_word (写) / ik_smart (读) | 标题，支持中文分词检索 |
| `body` | text | ik_max_word | 正文内容，全部分词 |
| `description` | text | ik_max_word | 描述信息 |
| `tags` | keyword | - | 标签数组，用于精确过滤 |
| `author_id` | long | - | 作者 ID |
| `author_avatar` | keyword | - | 作者头像 URL |
| `author_nickname` | keyword | - | 作者昵称 |
| `author_tag_json` | keyword | - | 作者领域标签 JSON |
| `publish_time` | date | - | 发布时间，用于排序 |
| `like_count` | integer | - | 点赞数，用于加权和排序 |
| `favorite_count` | integer | - | 收藏数，用于加权 |
| `view_count` | integer | - | 浏览数，用于加权和排序 |
| `status` | keyword | - | 状态 (published/deleted)，用于过滤 |
| `img_urls` | keyword | - | 图片 URL 数组 |
| `is_top` | keyword | - | 是否置顶 |
| `title_suggest` | completion | - | 标题补全建议 |

### 5.2 中文分词策略
**写时分词 (analyzer)**:
- `ik_max_word`: 尽可能细粒度切分，提高召回率
- 例："中华人民共和国" → ["中华", "华人", "人民", "共和", "共和国"...]

**读时分词 (search_analyzer)**:
- `ik_smart`: 粗粒度切分，提高准确率
- 例："中华人民共和国" → ["中华人民共和国"]

**配置示例**:
```json
"title": {
  "type": "text",
  "analyzer": "ik_max_word",      // 写入时使用细粒度
  "search_analyzer": "ik_smart"   // 查询时使用粗粒度
}
```

## 六、搜索逻辑详解

### 6.1 宽召回策略
**多字段匹配**:
```java
multi_match(query)
  .fields("title^3", "body")  // 标题权重是正文的 3 倍
```

**优势**:
- 标题通常更精炼，权重更高
- 正文提供更全面的上下文
- 平衡准确性和召回率

### 6.2 业务过滤
**状态过滤**:
```java
filter: { term: { "status": "published" } }
```
- 只展示已发布内容
- 软删除内容自动过滤

**标签过滤**:
```java
filter: { terms: { "tags": ["标签 1", "标签 2"] } }
```
- 支持多标签 OR 匹配
- 满足垂直分类搜索需求

### 6.3 业务加权
**互动数据加权函数**:
```java
function_score {
  functions: [
    {
      field_value_factor: {
        field: "like_count",
        modifier: "log1p",  // log(1 + x) 避免极端值
        weight: 2.0         // 点赞权重更高
      }
    },
    {
      field_value_factor: {
        field: "view_count",
        modifier: "log1p",
        weight: 1.0         // 浏览权重较低
      }
    }
  ],
  boost_mode: "sum"  // 与相关性分数相加
}
```

**设计考量**:
- 使用 `log1p` 平滑处理，防止马太效应
- 点赞比浏览更能体现内容质量
- 加权模式选择 `sum`，兼顾相关性和热度

### 6.4 复合排序
**排序优先级**:
```java
sort: [
  { _score: "desc" },           // 1. 相关性优先
  { publish_time: "desc" },     // 2. 新内容优先
  { like_count: "desc" },       // 3. 高赞优先
  { view_count: "desc" },       // 4. 热门优先
  { content_id: "desc" }        // 5. 稳定排序 (避免重复/跳页)
]
```

**为什么需要 content_id 排序？**
- 前五者可能完全相同 (罕见但可能)
- 添加唯一字段保证排序稳定性
- 避免分页时结果重复或遗漏

### 6.5 游标分页
**传统分页的问题**:
```sql
-- 深度分页性能差
LIMIT 10000, 20  -- 需要扫描前 10020 条
```

**游标分页方案**:
```java
// 第一次查询
search_after: null
→ 返回 results[20], nextAfter = "base64(sort_values)"

// 第二次查询
search_after: decode(nextAfter)
→ 返回下一批结果
```

**优势**:
- 性能稳定，不随页码增长下降
- 基于快照语义，避免数据跳变
- 适合移动端无限滚动场景

### 6.6 高亮显示
**高亮配置**:
```java
highlight: {
  fields: {
    "title": {},
    "body": {}
  }
}
```

**片段合并**:
```java
// 拼接标题和正文的高亮片段
snippet = join(highlight.title, highlight.body)
// 使用空格分隔，形成完整摘要
```

**效果**:
```html
标题：<em>知光</em>平台介绍
正文：欢迎使用<em>知光</em>...
```

## 七、高亮与联想

### 7.1 高亮实现
**技术选型**: ES 内置高亮功能

**配置要点**:
- 对 `title` 和 `body` 字段启用高亮
- 使用默认的 `<em>` 标签包裹
- 自动截取包含关键词的片段

**前端处理**:
```javascript
// 直接渲染 snippet 字段即可显示高亮
<div v-html="item.description"></div>
```

### 7.2 联想建议
**Completion Suggester**:
```java
suggest: {
  "title_suggest": {
    prefix: "知",
    completion: {
      field: "title_suggest",
      size: 10
    }
  }
}
```

**工作原理**:
1. 索引时将标题存入 `title_suggest` (completion 类型)
2. 查询时根据前缀匹配
3. 返回完整的标题文本

**优势**:
- 基于有限状态自动机 (FST),速度极快
- 支持前缀匹配，符合搜索习惯
- 返回结果可控，避免过度暴露

## 八、性能优化

### 8.1 写入优化
**批量回灌**:
- 分页读取，每批 500 条
- 避免一次性加载过多数据
- 支持断点续传

**刷新策略**:
```java
refresh: WaitFor  // 等待刷新保障立即可搜
```
- 平衡实时性和性能
- 避免频繁刷新影响吞吐

### 8.2 查询优化
**字段裁剪**:
- 只返回必要字段
- 减少网络传输开销

**缓存策略**:
- ES 内部 Query Cache
- 热点数据 Redis 缓存 (可扩展)

### 8.3 容错处理
**安全抓取正文**:
```java
try {
    // 尝试从 URL 抓取正文
    // 失败则使用 description 字段
} catch (Exception e) {
    // 记录日志，不中断索引流程
}
```

**异常降级**:
```java
catch (Exception e) {
    return new SearchResponse(Collections.emptyList(), null, false);
}
```
- 搜索失败返回空结果，不抛异常
- 保证系统可用性

## 九、扩展性设计

### 9.1 多内容类型支持
当前设计已预留 `content_type` 字段，未来可支持:
- 图文 (image_text)
- 视频 (video)
- 音频 (audio)
- 纯文本 (text)

**扩展方式**:
```java
// 在 filter 中添加类型过滤
bq.filter(f -> f.term(t -> t.field("content_type").value(v -> v.stringValue("video"))));
```

### 9.2 个性化搜索
基于 `currentUserIdNullable` 可实现:
- 搜索历史推荐
- 个性化加权 (根据用户偏好)
- 权限过滤 (私有内容可见性)

### 9.3 聚合统计

```java
// 按标签聚合统计
aggs: {
  "tags_agg": {

```

## 十一、总结

### 11.1 核心优势
1. **中文友好**: IK 分词完美支持中文检索
2. **性能优异**: 毫秒级响应，支持高并发
3. **扩展性强**: 易于添加新字段和新功能
4. **维护简单**: 自动化程度高，人工干预少

### 11.2 设计亮点
1. **读写分离**: 写入异步不影响读取体验
2. **冗余换性能**: 列表字段冗余减少 DB 查询
3. **多级排序**: 相关性 + 时效性 + 热度综合排序
4. **游标分页**: 解决深度分页性能问题

### 11.3 未来规划
1. **智能推荐**: 结合用户行为优化排序
2. **拼写纠错**: 自动纠正输入错误
3. **同义词扩展**: 提升召回率
4. **热搜榜单**: 挖掘热门搜索词
